# 音视频播放链路性能报告

本次分两轮调整高频播放路径，每轮使用固定媒体进行真机基准测试并独立提交

## 测试环境与口径

- 设备：Raspberry Pi Compute Module 0 Rev 1.0，361392 KiB RAM
- 系统：Linux 6.18.39+rpt-rpi-v8，320 × 170 RGB565 屏幕
- CPU：ondemand，600–1000 MHz，采样结束时记录频率和温度
- 编译：Rust 1.97.1，aarch64-unknown-linux-musl，release，opt-level=z，LTO
- 解码器：所有版本复用设备上的同一份 cardbili-ffmpeg，SHA-256 为 `df5886c79ba6e87f4b9ce412b63921c049b0d57d81915140db4cada585999903`
- 输入：80 秒的 640 × 360、30fps H.264 测试图，800 kbit/s 目标码率，44.1 kHz 双声道 AAC 静音音轨，FLV 封装
- 媒体通过设备本机 HTTP 提供，保留正式播放器的输入参数，排除外部网络与直播内容变化
- 固定中文和 emoji 标题，每 0.5 秒注入一条中文 emoji 弹幕，使用直播帧队列与实际音频时钟
- 每版测试控件隐藏、控件持续显示两种状态，各重复 3 次，每次运行 35 秒
- 前 5 秒预热，内部计时统计后续 30 秒；进程资源使用 `/proc` 在约第 5.5–33.5 秒的差值采样
- CPU 百分比以单核 100% 计，RSS 为采样窗口平均驻留内存，结果汇总为三次测试的算术平均
- P95 列为三次测试各自 P95 的平均值，帧率为测量窗口内提交新画面的次数除以 30 秒
- 测试期间暂停 APPLaunch，结束后恢复；使用独立的配置、缓存和状态目录

计时探针由 `scripts/benchmarks/playback.py prepare` 注入临时源码副本，正式应用源码和二进制不含探针。原始数据保存在同目录的 JSON 文件，CPU 统计覆盖主程序、FFmpeg 和 pacat，显示耗时覆盖真实 framebuffer 提交

## 原始实现

代码基线为 `d83b2a2`，视频路径为：FFmpeg 输出 → Vec 读取 → 整帧 clone 入队 → Slint 像素缓冲分配和复制 → 软件合成 → RGB565 提交

每个 RGB24 帧为 163200 字节，每秒显示 30 帧时，两次额外复制合计搬运约 9.792 MB 像素数据。15 帧队列的像素载荷约 2.448 MB

## 第一轮：统一像素缓冲

- 读取线程直接填充 `SharedPixelBuffer<Rgb8Pixel>`，帧队列和 UI 移交同一份缓冲区所有权
- 删除读取后的整帧 clone，以及 UI 中的第二次分配和复制
- 保留 15 帧队列、音频时钟、暂停、丢帧和直播缓冲等待逻辑
- 每帧仍有一次像素缓冲分配，管道读取、软件渲染和屏幕提交沿用当前实现

| 控件状态 | 版本 | 主程序 CPU | 主程序 RSS | 帧交接均值 | UI 同步均值 | 视频帧率 |
|---|---|---:|---:|---:|---:|---:|
| 隐藏 | 原始 | 27.99% | 9.16 MiB | 1.396 ms | 0.892 ms | 29.58fps |
| 隐藏 | 第一轮 | 24.48% | 9.32 MiB | 0.014 ms | 0.268 ms | 29.51fps |
| 显示 | 原始 | 33.90% | 9.12 MiB | 1.396 ms | 0.883 ms | 29.51fps |
| 显示 | 第一轮 | 30.69% | 9.39 MiB | 0.014 ms | 0.261 ms | 29.51fps |

12 组测试均未出现超过 100ms 的新画面提交间隔。第一轮主要降低帧交接与 UI 同步成本，帧率仍受固定 30fps 输出约束

第一轮基准二进制 SHA-256：`9c41dadd31cb7ec81f0edff56b77a01fad80231717fd8b9aec92b8c1b9d941c4`

## 验证与适用范围

ARM64 正式主程序和桌面 `cargo check --locked --features desktop` 编译通过，真机截图确认视频、中文 emoji 弹幕及播放控件正常显示

构建入口完成 Rust 主程序后，附带的 FFmpeg Docker 构建因 Docker Hub 连接重置失败。本轮未修改 FFmpeg，所有基准复用同一个已安装解码器，Rust 主程序编译和真机测试已完成

固定测试图用于比较应用高频路径。真实直播的源分辨率、编码复杂度、网络中断和音频内容会影响绝对 CPU 占用，本报告的性能比例适用于上述固定负载

## 复现方式

生成固定媒体，本次生成器为 FFmpeg 9.0.2，媒体 SHA-256 为 `8c7b23e5be54e4b7703a82056df72777474992502cee24b7dfaa6351436b8cb6`

```sh
ffmpeg -hide_banner -loglevel error \
  -f lavfi -i testsrc2=size=640x360:rate=30 \
  -f lavfi -i anullsrc=r=44100:cl=stereo -t 80 \
  -c:v libx264 -preset veryfast -b:v 800k -pix_fmt yuv420p -g 60 \
  -c:a aac -b:a 64k -f flv /tmp/fixture.flv
```

为各版本单独准备临时源码，并使用项目相同的 Rust 编译参数构建。以下示例将原构建脚本中的 FFmpeg Docker 步骤移除，基准继续使用设备现有解码器

```sh
python3 scripts/benchmarks/playback.py prepare "$PWD" /tmp/cardbili-bench-build
mkdir -p /tmp/cardbili-bench-build/scripts
sed '/^docker build /d' scripts/build-device.sh > /tmp/cardbili-bench-build/scripts/build-device.sh
bash /tmp/cardbili-bench-build/scripts/build-device.sh
```

将临时构建产物、固定媒体和 `scripts/benchmarks/playback.py` 复制到设备测试目录，在测试二进制同目录放置指向已安装 `cardbili-ffmpeg` 的符号链接。暂停 APPLaunch 后运行，每种控件状态重复 3 次，完成后恢复启动器

```sh
python3 playback.py run ./candidate ./fixture.flv hidden ./results/hidden-1.json
python3 playback.py run ./candidate ./fixture.flv visible ./results/visible-1.json
```
